# RecruitFlow — Handoff Document

## What this is

A full-stack recruitment pipeline management system. Two roles (Recruiter, Interviewer) collaborate on moving candidates through a fixed hiring pipeline, with strict server-side business rules and a permanent audit trail.

**Status: Feature-complete, deployed to production. Live at:**
- **Frontend**: Vercel (`https://<your-app>.vercel.app`)
- **Backend API**: Render (`https://recruitflow-api.onrender.com`)
- **Database**: Neon Tech (Serverless PostgreSQL)

## What's done

### Backend (100% of the 10 master requirements)
- Auth (JWT in `HttpOnly` cookie), role-based + resource-level authorization
- Job openings: CRUD, archive/restore (applications survive archiving)
- Applications: CRUD, tied to exactly one job
- Pipeline state machine: strict forward transitions, rejection from any active stage, reinstatement to exact prior stage
- Interview panel (role-restricted to `INTERVIEWER` users) + interview scheduling
- Interviewer feedback (assignment-enforced, append-only)
- Global search/filter/sort/server-side pagination
- Bulk advance/reject with per-item results
- CSV export
- Dashboard (6 metrics/breakdowns, all from real queries)
- Immutable append-only history (no update/delete route exists anywhere for it)
- Stalled alerts (10-day threshold, per-stall-episode dismissal that reappears on re-stall)

**Testing**: 68 automated pytest tests, all passing.

### Frontend (all core pages, visually verified in browser)
- Login
- Dashboard (metrics, by-job/by-stage breakdowns, weekly chart)
- Applications (search, filter, sort, pagination, multi-select, bulk actions with visible per-item results)
- Job Openings (list, create/edit, archive/restore)
- Application Detail (pipeline stepper, panel management, feedback, interview scheduling, full timeline)
- Alerts (list, dismiss)
- My Interviews (interviewer's own applications + interviews)

**Frontend**: React 19 + TypeScript + Vite. Built and verified in browser end-to-end (both Recruiter and Interviewer roles).

### DevOps / Deployment
- `render.yaml` — Render deployment manifest for backend (web service, free tier)
- `frontend/vercel.json` — SPA rewrite rules for Vercel
- Alembic migrations auto-applied at startup via `render.yaml` startCommand
- `seed.py` auto-runs at startup to populate demo data
- `.env.example` files for both frontend and backend
- `.gitignore` (env files never committed)

## Deployment Architecture

```
Browser
  |
  v
Vercel (Frontend — React SPA, static)
  |  HTTPS API calls with credentials
  v
Render (Backend — FastAPI, Python, Free Web Service)
  |  SQLAlchemy / psycopg2
  v
Neon Tech (PostgreSQL — Serverless, Free Tier)
```

### Environment Variables

**Backend (set in Render dashboard):**

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon connection string (pooled, `postgresql+psycopg2://...?sslmode=require`) |
| `CORS_ORIGINS` | Your Vercel frontend URL (e.g. `https://recruitflow.vercel.app`) |
| `JWT_SECRET_KEY` | Auto-generated by Render (`generateValue: true` in render.yaml) |
| `ENVIRONMENT` | `production` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `1440` |

**Frontend (set in Vercel dashboard):**

| Variable | Value |
|---|---|
| `VITE_API_URL` | Your Render backend URL (e.g. `https://recruitflow-api.onrender.com`) |

> **Important**: The Neon DATABASE_URL must use `?sslmode=require` at the end and the `postgresql+psycopg2://` prefix (not `postgres://`). Neon provides the URL with `postgres://` — replace it manually.

### Known Deployment Gotchas (already resolved)

1. **Render free tier cold starts**: The backend sleeps after 15 min of inactivity. First request after sleep takes 30-60 seconds. This is expected behavior — not a bug.
2. **Neon SSL requirement**: Neon requires `sslmode=require` in the connection string. Without it, SQLAlchemy raises a connection error at startup.
3. **CORS_ORIGINS must be exact**: No trailing slash. Must match the exact Vercel URL the browser navigates to.
4. **`vercel.json` rewrite rule**: Required for React Router — without it, direct navigation to `/dashboard` returns a 404 from Vercel. Already configured in `frontend/vercel.json`.
5. **Seed data**: `seed.py` runs on every deploy start. It is idempotent (checks for existing data before inserting), so re-deploys don't create duplicate users/jobs.
6. **Blank white page on navigation**: Was caused by React Router not finding routes on direct URL access. Fixed by the `vercel.json` SPA rewrite rule.

## Where to look when something breaks

- **"Network error" on login from frontend** → Check `VITE_API_URL` in Vercel env vars AND `CORS_ORIGINS` in Render env vars. Both must be set correctly and match exactly.
- **Backend Render deploy fails** → Check Render logs. Most common cause: `DATABASE_URL` wrong format (must be `postgresql+psycopg2://`, not `postgres://`). Also check for Neon SSL requirement.
- **Blank white page after navigation** → `vercel.json` rewrite rule is missing or misconfigured. Current `vercel.json` already fixes this.
- **Business logic bugs** → `backend/app/services/` (routes are thin; almost all logic lives here)
- **"WHY does X behave this way"** → inline `WHY` comments in the relevant service file
- **Auth/permission bugs** → `backend/app/core/deps.py` (the entire authorization system, ~80 lines, all in one file)
- **Frontend data not updating after an action** → Check the TanStack Query `invalidateQueries` calls in the relevant `src/api/*.ts` hook — missing invalidation is the most likely cause of stale UI

## What's NOT done (remaining improvements)

1. **No CI pipeline**: Tests pass locally; nothing runs them automatically on push. Consider GitHub Actions running `pytest` + `npm run build` on every PR.
2. **Bundle size**: Frontend JS bundle is ~725KB uncompressed (mostly Recharts). Not broken, but worth lazy-loading the Dashboard route (`React.lazy`) before a high-traffic launch.
3. **No rate limiting**: No rate limit on `/auth/login`. Low priority for internal tools, worth adding before public exposure.
4. **No production logging/monitoring**: No structured log aggregation or error tracking (e.g. Sentry). Console logs only.
5. **Email uniqueness race condition**: Under concurrent registrations with the same email there's a narrow window where a 500 surfaces instead of a clean 400 (the DB constraint still prevents the duplicate). Fix with `try/except IntegrityError` if needed.
